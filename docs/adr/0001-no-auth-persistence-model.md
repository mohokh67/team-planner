# No-auth persistence: Supabase, UUID read-key + edit-token write-key checked server-side

The app is a static GitHub Pages site with no backend of its own, but needs Plans to persist and be reachable from any browser, not just the one that created them. We chose Supabase as the store. Without real authentication every anonymous request looks identical, so RLS on a single `plans` table can't distinguish "the caller who legitimately knows this Plan's UUID" from anyone else by row — a naive `using (true)` policy on that table would also make any column on it, including an edit token stored alongside the rest of the row, readable by anyone who can read the Plan at all, collapsing read access into write access.

So the edit token isn't a column anyone can read: it lives in its own `plan_secrets` table with no anon policies at all (default-deny). The Plan's UUID is the read key — the `plans` table (name, unit, people, tickets) is openly readable by anon. The edit token is the write key: every write goes through a `security definer` Postgres function (`update_plan`, `delete_plan`) that checks the supplied token against `plan_secrets` before touching `plans`, so possession of the UUID alone never yields possession of the token. Both the UUID and the token are still carried in the URL and cached in localStorage as bearer secrets on the client side — that part of the model didn't change — but now the database enforces the token check itself instead of trusting the app never to send an unauthorized write.

Security still rests on the token being practically unguessable (128-bit random) and on the app never exposing a "list all Plans" query. This is a deliberate tradeoff for a low-stakes, single-user planning tool — real per-Plan authorization would require adding actual authentication, which was explicitly ruled out.

Considered and rejected:
- A single `plans` table with the edit token as a plain column and open RLS on all of read/insert/update/delete — the initial design; rejected after review because it let anyone who could read a Plan (i.e. anyone with just its UUID) also read its edit token directly, defeating the read/write split entirely.
- RLS policies keyed on the Plan UUID itself — doesn't work, since RLS cannot verify a request "knows" the UUID it's filtering on versus an attacker enumerating rows.
