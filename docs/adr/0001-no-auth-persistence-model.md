# No-auth persistence: Supabase, UUID read-key + edit-token write-key checked server-side

The app is a static GitHub Pages site with no backend of its own, but needs Plans to persist and be reachable from any browser, not just the one that created them. We chose Supabase as the store. Without real authentication every anonymous request looks identical, so RLS can't distinguish "the caller who legitimately knows this Plan's UUID (or edit token)" from anyone else — a `using (true)` policy doesn't mean "rows whose id matches what the caller asked for," it means "every row, to every caller with this role," because RLS has no way to see what a query's `WHERE` clause happens to be. The client's `apikey` (the anon key) also ships inside the static bundle served to every visitor, so it must be treated as fully public, not as a secret that limits who can query the API.

So no table has any RLS policy for `anon` at all, for any operation — both `plans` and `plan_secrets` are pure default-deny. Every read and every write goes through a `security definer` Postgres function that takes the relevant id (and, for writes, the edit token) as a typed parameter and checks it explicitly in SQL, instead of asking RLS to do something it structurally can't: `get_plan`/`get_plan_names` return only the row(s) matching the id(s) passed in; `create_plan`/`update_plan`/`delete_plan` check the supplied token against `plan_secrets` before touching `plans`. The edit token itself never appears in any function's return value, so knowing a Plan's UUID (the read key) never yields its edit token (the write key). Both are still carried in the URL and cached in localStorage as bearer secrets on the client side — that part of the model is unchanged — but the database now enforces both the per-id scoping and the token check itself, rather than trusting the app's queries to always include the right `WHERE`/`eq()`.

Security still rests on the UUID and token being practically unguessable (128-bit random) and on the app never exposing a "list all Plans" query. This is a deliberate tradeoff for a low-stakes, single-user planning tool — real per-Plan authorization would require adding actual authentication, which was explicitly ruled out.

Considered and rejected:
- A single `plans` table with the edit token as a plain column and open `using (true)` RLS for anon on read/insert/update/delete — the initial design; rejected after review because it let anyone who could read a Plan (i.e. anyone with just its UUID) also read its edit token directly, defeating the read/write split entirely.
- An open `using (true)` SELECT policy on `plans` alone, with the edit token already split out into `plan_secrets` — the second iteration; still rejected, because `using (true)` grants the *entire table* to anon regardless of which id a query asks for. Since the anon key is public by construction, this meant anyone could dump every Plan ever created with a single unauthenticated REST call, independent of the app's own UI (which happens to always filter by id, but that's a client convention PostgREST doesn't enforce) — contradicting the "UUID is the read key" model this ADR describes. Reads now go through `get_plan`/`get_plan_names` for the same reason writes go through functions: RLS can't scope by a caller-supplied id, only a function body can.
- RLS policies keyed on the Plan UUID itself — doesn't work, since RLS cannot verify a request "knows" the UUID it's filtering on versus an attacker enumerating or simply omitting a filter.
